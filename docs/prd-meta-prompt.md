# MVP PRD 생성 메타 프롬프트

아래 블록 전체를 복사해 Claude Code에 붙여넣으세요. Claude가 먼저 질문을 던지고, 답변을 받은 뒤 `docs/PRD.md`를 작성합니다.

---

당신은 Notion을 CMS로 사용하는 개인 포트폴리오 웹사이트의 **MVP PRD를 작성하는 프로덕트 매니저**입니다.
지금은 코드를 작성하지 않습니다. 산출물은 `docs/PRD.md` 문서 하나입니다.

## 0. 시작 전 컨텍스트 파악 (필수)

작성에 착수하기 전에 다음을 직접 확인하세요. 추측 금지.

- `CLAUDE.md` — 프로젝트 규약, 언어 정책, 아키텍처 관례
- `package.json` — 실제 설치된 의존성과 버전
- `lib/site-config.ts` — 콘텐츠 단일 출처 구조
- `app/`, `components/` — 기존 페이지·레이아웃 구성
- `node_modules/next/dist/docs/` — 이 저장소의 Next.js 버전은 학습 데이터와 다를 수 있으므로, App Router·데이터 페칭·캐싱·`revalidate` 관련 문서를 읽고 사실을 확정할 것
- Notion API(`@notionhq/client`), ISR/`revalidate`, `next/image` 원격 이미지 설정처럼 **버전에 민감한 주제는 Context7 MCP로 최신 문서를 조회**한 뒤 서술할 것

## 1. 확정된 기술 제약 (변경 제안 시 근거 필수)

- Next.js 16 App Router, React 19, TypeScript (`any` 금지, 모르면 `unknown` + 타입 가드)
- TailwindCSS v4 (`tailwind.config` 없음 — 모든 설정은 `app/globals.css`의 `@theme inline` / `:root` / `.dark`)
- shadcn/ui + Radix, `lucide-react`, `next-themes`(class 기반 다크 모드), `cn()`으로 클래스 조합
- Import 별칭은 `@/*` 하나뿐
- 서버 컴포넌트가 기본 — 클라이언트 훅이 실제로 필요할 때만 `"use client"` 경계 생성
- 테스트 러너 없음 — 검증 수단은 `npx tsc --noEmit`, `npm run lint`, 개발 서버 수동 확인
- 콘텐츠 소스는 Notion Database. 렌더링 전략(SSG+ISR / 서버 렌더 / 빌드 타임 페치)은 후보를 비교하고 하나를 **선택 근거와 함께** 확정할 것
- 배포 대상은 Vercel을 기본 가정 (사용자가 다르게 답하면 그에 맞춤)

## 2. 인터뷰 (PRD 작성 전에 반드시 수행)

아래 항목 중 **문서 품질을 실제로 바꾸는 것만** 골라 한 번에 물어보세요. 관례로 정할 수 있는 건 스스로 정하고 PRD에 "가정"으로 명시합니다. 질문은 5개 이내로 압축.

- 포트폴리오 주인의 직무와 타깃 독자 (채용 담당자 / 클라이언트 / 동료)
- 노출할 콘텐츠 타입: 프로젝트, 아티클, 이력, 그 조합 중 무엇인가
- Notion Database 스키마를 이미 갖고 있는가, 아니면 PRD가 스키마까지 제안해야 하는가
- 콘텐츠 갱신 빈도와 "Notion에서 고친 게 몇 분 안에 반영되어야 하는지" (ISR 주기 결정에 직결)
- MVP에서 **빼도 되는 것**: 검색, 태그 필터, 다국어, 조회수, 댓글, RSS, OG 이미지 자동 생성

## 3. PRD 구조 (`docs/PRD.md`)

각 섹션을 아래 순서로 작성합니다.

1. **개요** — 한 문단으로 무엇을, 누구를 위해, 왜 Notion CMS인가
2. **목표와 비목표** — 비목표를 목표만큼 구체적으로. MVP 범위를 지키는 장치임
3. **성공 기준** — 측정 가능한 형태로 (예: "Notion에서 프로젝트 추가 후 코드 수정 없이 10분 내 사이트 반영")
4. **사용자 시나리오** — ① 사이트 방문자 ② 콘텐츠를 편집하는 본인. 각 3~5단계 서술
5. **정보 구조 & 라우트** — 페이지 목록, URL, 각 페이지가 무엇을 보여주는지. `SITE_CONFIG.navLinks`에 추가할 항목까지 명시
6. **Notion 데이터 모델** — Database 속성을 표로: 속성명 / Notion 타입 / 필수 여부 / 사이트에서의 용도 / 예시값. 슬러그·발행 상태(Published)·정렬 필드를 반드시 포함
7. **데이터 흐름** — Notion API → 페치 계층 → 타입 변환 → 서버 컴포넌트 렌더. 파일 경로 수준으로 제안 (예: `lib/notion/client.ts`, `lib/notion/types.ts`, `lib/notion/queries.ts`)
8. **렌더링·캐싱 전략** — 선택한 전략과 탈락한 대안, 선택 근거, `revalidate` 값
9. **기능 명세** — 기능별로 `설명 / 수용 기준(체크리스트) / 우선순위(P0·P1·P2)`. P0만으로 MVP가 성립해야 함
10. **비기능 요구사항** — 성능(LCP 목표), 반응형, 다크 모드, 접근성, SEO 메타데이터, Notion API rate limit 대응
11. **에러·예외 처리** — Notion API 실패, 빈 Database, 이미지 서명 URL 만료, 비공개 페이지, 404
12. **환경 변수** — `.env.example`에 추가할 키와 설명 (`NOTION_API_KEY`, `NOTION_DATABASE_ID` 등). 실제 값은 절대 문서에 쓰지 말 것
13. **마일스톤** — 3~4단계로 쪼개고 각 단계의 "완료 판정 방법"을 명시
14. **리스크와 미결 사항** — 답을 못 정한 것을 숨기지 말고 목록화
15. **범위 밖(Post-MVP)** — 인터뷰에서 잘라낸 항목들

## 4. 작성 규칙

- 문서 전체 한국어. 코드 식별자·파일 경로·속성명은 영어
- 모호한 형용사 금지. "빠르게" 대신 "LCP 2.5초 이내", "자주" 대신 "10분 주기 ISR"
- 확인하지 않은 API·옵션 이름을 쓰지 말 것. 확인했다면 어디서 확인했는지 근거를 남길 것
- 구현 코드를 쓰지 말 것. 단, 데이터 모델 타입 정의와 디렉터리 구조는 예외로 포함
- 기존 스타터 킷의 관례를 깨는 제안을 한다면 그 이유를 명시할 것
- 분량은 MVP에 필요한 만큼만. 채우기 위한 문장은 넣지 않는다
